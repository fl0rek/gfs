# pi on gfs — prototype

**Throwaway.** This is a single-node, browser-only prototype built to feel out the shape of Universal Explorer: a coding agent whose entire world is a versioned filesystem. Nothing here is the architecture; it exists to be reacted to.

What it is:

- **pi** (`@earendil-works/pi-agent-core` + `pi-ai`) runs in a **Web Worker**. Its four tools (`read`, `write`, `edit`, `bash`) are reimplemented over gfs with pi's own schemas, so a real model sees the tools it knows.
- **gfs** is a Rust crate compiled to wasm (`gfs-core/`): content-addressed objects (BLAKE3), trees, and a hash-chained history per comb. Every tool call that changes a comb becomes **one history entry** attributed to that call (tool name, call id, turn, args stored by hash, author = the session, committer = the node). Rollback appends an entry; nothing is rewritten. The chain can be verified.
- **bash is real, and gfs is mounted into it.** GNU bash (WASIX, built by the flake in `machine/`) runs under the Wasmer JS SDK's runtime in the same worker, with gfs as three host mounts: `/datacombs` (every comb, plus `<comb>@<entry>` read-only views of the past), `/nix`, and `/machine`; cwd `/datacombs`. Every filesystem call under those paths is answered from gfs by this worker (`web/src/hostfs.ts`), through the SDK's experimental host-filesystem hook (`mountHost` on the core's sandbox builder, a synchronous SharedArrayBuffer RPC from the pool workers; protocol read from `js/bindgen/src/host_filesystem.rs`). No copy in or out: what a command writes is in the comb as it writes it, and becomes one history entry like any other tool call. A trivial command costs ~30 ms. Every module is pinned by sha256 in `/nix/machine.json` and served from our own origin.
- **Persistence** is OPFS: every object and ref is written as it is created and loaded back on start. Reload the tab; the history, the files and the conversation are still there.
- **The conversation is itself a comb** (`/datacombs/session`): the transcript is committed once per turn, so "what was said" and "what changed" live in the same kind of history.
- **Network**: pi has a `fetch` tool. A page can only fetch what CORS allows, so `prototype/extension/` is the escape hatch: a WebExtension that relays fetches with host permissions; the worker falls back to it whenever a direct fetch is refused, for the tool and for the LLM calls alike. No relay server anywhere. bash has no sockets (an extension can't give TCP).
- **`/nix`**: a comb holding the running system's flake (`flake.nix`) and its built form (`machine.json`: the packages the shell sandbox loads, each pinned by sha256). A change to `machine.json` is committed only if the system it describes boots: the new sandbox is built first; then the change lands as an entry, followed by a `switch` entry of its own kind (which entry is now running, which was before), shown in every comb's timeline; if it doesn't boot (bad hash, missing package) the working tree is reset and whoever made the change (pi's tool, the editor, the shell) gets the refusal. So `/nix`'s head is always the running system, and rollback on `/nix` obeys the same rule. The header shows `system /nix@<entry>`.
- **`/machine`**: the node describing itself, read-only and generated on read, visible to pi and to bash: `session`, `system`, `shell` (packages, commands, switches), `processes` (every command spawned: who, wall time, exit, combs changed), `runtime` (SDK version, the runtime's own heap, isolation, host hints), `agent` (turns, tool calls, token usage and cost, the free-tier router), `storage` (combs, objects, OPFS usage/quota), `egress`, `mounts`, `uptime`. Guest memory, CPU, the guest process table and syscall counts live inside the runtime and need it patched to come out.
- **`machine/`**: the Nix flake that builds that system: a WASIX toolchain (stock nixpkgs LLVM 20 + binaryen + the prebuilt wasix-libc sysroot, flags from wasixcc) and GNU bash 5.2 (wasix-org fork), coreutils 9.12, grep, sed, gawk, findutils and diffutils as WASIX wasm: 12 modules, 108 commands, 18 MB. CI runs `nix build .#machine` and the web build turns its output into the deployed `machine.json`, so the hosted site runs a system that is 100 % Nix-built and never talks to wasmer.io (the registry packages remain only as a fallback when the flake isn't built). `machine/NOTES.md` has the build log, the gnulib cross-compile fixes, and the three Wasmer-runtime quirks shimmed in `compat/wasix-quirks.c` (lseek/fstat on pipes, `program_invocation_name`).
- **The view** (`/nix/view/index.html`): a second surface you switch to from the header. Its page is a file in the `/nix` comb, rendered in a sandboxed iframe with `window.ue` (a snapshot of `/machine`, refreshed every few seconds, plus `ue.prompt(text)` to message pi) and re-rendered on every history entry of `/nix`. So pi (or you, in the Files editor or with `!cmd`) programs what is shown there, every change is an entry, and rollback on `/nix` rolls the view back too. You switch surfaces; the harness only controls what is inside. It is seeded with an introspection dashboard: uptime, system, shell, process tree (boot / pi's tool calls / your shell), `/machine`, mounts, combs.
- **More views, and WayQuest** (`/nix/view/<name>/index.html`): every `index.html` under `/nix/view/` is a view with its own tab in the header (console | view | wayquest); the first one re-renders on every `/nix` entry as before, the others when an entry touches their own directory. Views can now read gfs: `ue.combs`, `ue.list(dir)`, `ue.read(path)`, `ue.bytes(path)`, `ue.log(comb)` (read-only, by gfs path, so `/datacombs/<comb>@<entry>/…` is the past), `ue.onHistory(fn)` on any comb's new entry, and `ue.state`/`ue.setState` kept by the page across re-renders and reloads. The second view, seeded once into `/nix/view/wayquest/`, is [WayQuest](https://github.com/fl0rek/wayquest) tracking every comb in datacombs as one world: each comb a region with its own biome, a comb with a wayfinder map (`.scratch/<effort>/map.md`) drawn as that map's overworld, the others as land with a building; beside it, what needs you across every map, each comb's progress and newest entry, and the recent changes (each history entry that touched a map, replayed through WayQuest's change diff and credited to its session). WayQuest's own world crate does the parsing, sensing, layout and roads (as wasm, `world_bg.wasm` beside the page); the page draws with Kenney's sheets the way WayQuest's canvas does. Writing into `/datacombs/<new>/…` now creates a comb, so projects can exist. `scripts/wayquest-standalone.mjs` builds the view as one HTML file over a snapshot of git repositories, for looking at it outside the app; `test/views.mjs` covers it end to end.
- **Git backing**: any comb can be connected to a branch of a git repository (the **Git** button in the history pane). gfs stays the local truth; every history entry is pushed as **one git commit**, automatically, a moment after it lands, with the entry's provenance in trailers (`Gfs-Entry`, `Gfs-Kind`, `Gfs-Tool`, `Gfs-Tool-Call`, `Gfs-Turn`, `Gfs-Session`, `Gfs-Model`, …). The author is the session, the committer is the node (or the identity you set). Git objects are derived in Rust (`gfs-core/src/git.rs`: SHA-1 trees/commits from gfs trees, packfiles out, packfiles in with deltas); blobs are never stored twice. What gfs can't hold (exec bit, symlinks, submodules) rides in a per-remote mode overlay, so a cloned tree encodes back to the same git tree id. Someone else's commit arrives as a `pull` entry when the comb has nothing unpushed; when both sides moved the comb is **diverged** and nothing merges on its own: *keep mine* pushes a merge whose tree is ours, *take theirs* adds a `pull` entry and pushes our entries under it. Neither force-pushes. Connecting a fresh comb (another browser, a wiped one) pulls the remote's tree. `/machine/git` shows it all to the harness.
  - Two transports. **git smart HTTP** (`web/src/githttp.ts`, our own client: ref discovery, receive-pack, shallow upload-pack) talks to any git server, but from a page only where CORS allows: Forgejo/Gitea with `[repository] ACCESS_CONTROL_ALLOW_ORIGIN`, anything else through the egress extension or a CORS proxy. **GitHub REST API** (`web/src/github.ts`: Git Data blobs/trees/commits/refs) works from a plain tab, since api.github.com answers CORS; an empty repository is bootstrapped through the contents API and that commit is replaced by the first push.
  - Signing in: a pasted token for every forge (GitHub: fine-grained PAT with *Contents: read and write*; Forgejo: an access token with `write:repository`). **Forgejo OAuth2 + PKCE** (public client, no secret, redirect back to the page, refresh tokens) works from a plain tab once the admin enables `[cors]`. **GitHub device flow** (OAuth App or GitHub App with device flow on) needs the extension, because github.com's `/login/*` sends no CORS headers. Tokens live in this browser's `localStorage`, like model keys. The reasoning and sources are in `research/git-from-the-browser.md`.
- Two views inside the console: pi's console, and the timeline of a comb from genesis to now, with the conversation interleaved, per-entry diffs, the tool-call arguments, the tree at any point (`/datacombs/<comb>@<entry>`), rollback and chain verification. A Files view lets you edit a comb by hand; saving is an `external` entry, which on `/nix` is the hand-driven switch.

## Run it

Hosted build: https://fl0rek.github.io/gfs/ (deployed from this branch by `.github/workflows/prototype-pages.yml`).

Locally (needs Rust, `wasm32-unknown-unknown`, `wasm-bindgen-cli` 0.2.129, Node 22, pnpm):

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.129 --locked
./prototype/build-wasm.sh          # gfs-core → web/src/gfs-wasm/
cd prototype/web && pnpm install && pnpm dev
```

The dev server sends COOP/COEP headers (the WASIX runtime needs `SharedArrayBuffer`). On GitHub Pages, which cannot send headers, `coi-serviceworker.js` adds them; the first load reloads once.

Keys and model settings live in the browser's `localStorage`. Models: **free** rides whichever free tier is up, using [ANUS](https://github.com/anus-dev/ANUS)'s ranked list and rest rules (MIT; `web/src/free.ts`): paste keys for OpenRouter, Google, Groq, Cerebras or Mistral and each request goes to the best awake model you hold a key for, with refused ones resting (a minute on a rate limit, until UTC midnight on a daily cap) and a cut-off answer retried elsewhere. **mock** (default) is a scripted agent that writes, runs bash, edits and answers, so everything works offline. **DeepSeek** and **OpenCode Zen** are wired through pi-ai; paste a key in the console (kept in `sessionStorage`, sent straight to the provider from the worker; CORS is the provider's decision). "openai-compatible" takes any base URL.

Tests (headless Chromium; `CHROME=/path/to/chromium`, with `pnpm build && pnpm preview` running): `test/e2e.mjs [url] [--extension]` runs a prompt, rollback, reload, verification and a `!` command; `test/system.mjs` covers `/nix` switching (good manifest, bad hash, rollback, reload); `test/egress.mjs` the fetch paths with and without the extension; `test/editor.mjs` the hand edit of `/nix`; `test/offline.mjs` proves the shell runs with wasmer.io blocked; `test/views.mjs` the views and WayQuest (`--maps=comb:/path/.scratch/<effort>,…`); `test/git.mjs` the git backing end to end (it starts its own servers: `test/git-server.mjs`, git's own `git http-backend` with CORS, Basic auth and a Forgejo-style OAuth2+PKCE endpoint, the same without CORS as a github.com stand-in, and `test/fake-github.mjs`, the Git Data API slice over a real bare repository; every repository the browser writes is checked with `git log`/`show`/`fsck`). Build with `BASE_PATH=/` for local tests. `cargo test` in `gfs-core/` (the git tests compare against the `git` CLI).

## What this prototype says

- pi's core packages are pure fetch-based TypeScript and run in a worker unchanged. Only the tools and the "session" wrapper are Node-bound. pi was the right pivot from Hermes for a browser-first prototype.
- One entry per tool call falls out naturally when the harness's tools are ours: the tool wrapper commits after each call, and `turn_id` comes from pi's `turn_start` event. No hook into the harness was needed.
- The WASIX shell works in a nested worker, but the Wasmer SDK must not be bundled (it spawns its pool from `import.meta.url`); it is copied verbatim and loaded at runtime.
- The Wasmer SDK resolves a package's dependencies by name against its registry (URL baked into the wasm core, 0.19.1), so shipping the `.webc` bytes alone is not enough; replaying the registry's recorded answer from our origin is. Wasmer's coreutils package has no grep/sed/awk/find; the system prompt says so.
- Mounting gfs needed no runtime patch. The SDK's `mountHost` hook is not in the public TypeScript API but is reachable through `Wasmer.getCore()` + `SandboxBuilderCore` + the exported `Sandbox` class; the parent side must define both `__wasmerHandleFileSystemRpc` (calls relayed from pool workers) and `__wasmerHostFileSystem` (direct calls from the runtime's own context, e.g. the cwd check at WASI setup). Timestamps go over the wire as decimal nanosecond strings. gfs has no empty directories, so the mount keeps a set of them. Earlier findings that still hold: `sandbox.fs` refuses paths outside `/workspace`, and the guest's `/` is fresh per process.
- Before the mount, the shell's filesystem was a mirror: the SDK has no public custom-filesystem hook (there is an experimental host-filesystem RPC bridge used by their iOS prototype). The mirror is correct at tool-call granularity, which is the granularity history already has.
- Timeline + diff + "browse at @entry" + rollback-as-new-entry reads naturally; the conversation interleaved with entries is what makes "who changed what and why" legible.

- Git as a backing fits beside the comb's own chain rather than replacing it: one entry → one commit is a pure function of the entry, its git parent and the node's identity, so the gfs chain stays the truth and git is a mirror anyone can clone. GitHub's API, given the same author, committer, dates and message, returns exactly the commit ids `git.rs` computes (checked against the fake; real GitHub not yet).
- From a browser, the forge decides what is possible, not the protocol: a self-hosted Forgejo can be configured for push and OAuth sign-in straight from the tab; github.com allows only its REST API from a page, so OAuth sign-in there needs the extension (device flow) or a server holding a client secret.
- Not yet tested against a real Forgejo or real GitHub (this sandbox cannot reach either for writing); tested against `git http-backend` and a fake of GitHub's API.

Not here: replication, multi-node, signing, encryption, cache tier, Nix-built userland.
